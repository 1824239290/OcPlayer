下文的原生改动与 30 条专项结果属于实验版本，当前默认方案的证据见文末。

本轮继续处理用户在第一阶段修复后反馈的滚动观感波动。第一阶段解决了更新频率，
本轮减少逐帧位移的速度变化。Windows x64 / 60 Hz 本机，两种渲染模式各连续
采样 60 秒，专项 30 条断言、完整 C# 集成 411 条断言、真实 WinUI 回归 29 条
断言均通过。修改保留在基线 `13752862396ebf25543eef0d557e5f3058315cf1` 的工作区。

## 原因与修改

第一阶段统计的 `danmakuFrames` 证明了原生渲染被持续调用，但不能说明每帧运动
速度是否均匀。本轮基线采样中，音频时钟修正直接改变弹幕布局的媒体时间：约 5 秒
内逐帧速度的 P5 为 0.657×、P95 为 1.305×，还出现过一次更大的跳变。

Windows 原生弹幕改用 `DanmakuDisplayClock`，按单调显示时间和已提交播放倍速
推进位置，小误差只通过最多 ±2% 的速度变化消化。暂停、缓冲、恢复、跳转代次
变化、超过 0.5 秒的原生时间突变或刷新中断立即对齐。该时钟只用于弹幕布局；
视频、音频、字幕及进度保存继续使用原有播放时钟。

WinUI 的 `RenderingTime` 映射到绝对 QPC 秒数，传入 Windows 可选原生 ABI
`erika_presenter_render_tick_at_qpc`。内核通过三组 QPC / `Instant` 读数选择最窄
时间区间，避免跨语言调度延迟改变显示目标。旧 DLL 仍可依次回退到相对时间 ABI
或旧 Tick。窗口最小化、恢复与关闭沿用第一阶段的订阅管理。

应用层弹幕在同一显示时刻调用 `RenderPositionAt`；原生进度事件也锚定到该时刻，
避免事件处理延迟改变已绘制帧附近的坐标。时钟校正收紧为 ±2%。文字使用
`TranslateTransform.X` 保留小数位移，并关闭布局取整；活动/过期 ID 集合复用。

原生改动保存为 `Scripts/patches/player-danmaku-display-clock.patch`。
`prepare-kernel.ps1` 和 `build-windows.ps1` 都会应用补丁，并在收据记录其哈希。
必须重建并使用新的 `erika_capi.dll` 才能获得原生弹幕改进。

| P95 | 1.3051× | 1.0171× | 1.0200× |

原生弹幕视觉时钟与诊断中的实时媒体时钟最大差距为 133.77 ms。该差距包含显示
目标与诊断读取时刻的差异。DXGI 成功提交计数在原生采样间增加 3591；另存的
显示计数是异步累计值，其首次无效样本已排除，未将两种计数作为逐帧一一对应证明。

应用层同时记录真实文字横坐标，7130 个同条弹幕的相邻位移样本均向前；速度
P5 / 中位数 / P95 为 151.65 / 152.45 / 157.85 像素每秒。数值与本次窗口宽度、
字号和弹幕长度相关，只用于确认实际坐标随绘制时钟连续变化。

运行 Debug exe，设置独立绝对路径 `OCP_DATA_DIRECTORY`、
`OCP_CADENCE_NATIVE_DETAILS=1`，传入
`--verify-danmaku-cadence=<新结果目录> --open=<至少70秒带音轨的视频路径>`。
保持窗口可见即可复现最终专项。`OCP_CADENCE_SECONDS` 可将每种模式采样设为
2–60 秒。运动检查使用实际绘制时刻，另存较晚读取的墙钟外推值供诊断。

本轮覆盖 Windows x64 / 60 Hz 和本地合成视频。更高刷新率、ARM64、真实网络
片源及更高弹幕密度尚未实测；本轮数据衡量布局时钟、文字坐标和呈现计数，未使用
高速摄影测量显示器端到端运动。第一阶段记录见
[弹幕刷新验证](danmaku-smoothness-2026-11-18.md)。

## 使用修改前内核的应用层对照

用户随后提出内核升级时维护补丁的成本。为确认应用层优化是否独立于本轮原生
改动，将当前 C# Debug 程序复制到隔离目录，替换为本轮修改前的 `erika-before.dll`
（SHA256 `A58328D28ED6C3DE4B9D9E755F20D2C4FF98EE16224384DEAF25E539924979D2`）。
该 DLL 是项目原先使用的版本，包含既有项目补丁，但不含本轮新增视觉时钟/QPC 补丁。

两种模式各约 5 秒的对照专项通过 29 条断言。应用层模式记录 300 个显示回调，
299 个相邻帧持续推进，回调中位数 16.6577 ms、P95 18.6914 ms，绘制时钟速度
保持约 0.98×，没有倒退；暂停、跳转、倍速、最小化/恢复及关闭检查也通过。
旧 DLL 没有原生视觉时钟诊断字段，因此此对照没有验证原生弹幕的逐帧速度。

证据位于 `app-with-original-kernel/`，包括隔离程序、旧 DLL 哈希、
`smoke-5s/results.json`、逐帧样本和退出码 0。结果确认应用层方案可以保留平滑
优化并撤掉本轮新增原生补丁。正式改用该方案仍需调整默认渲染路线和构建依赖；
应用层当前最多同时绘制 400 条弹幕，更高密度的性能尚未验证。本次对照没有改变
用户设置或撤掉当前工作区的原生补丁。
