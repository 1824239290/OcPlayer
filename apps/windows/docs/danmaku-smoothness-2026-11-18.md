# Windows 弹幕滚动卡顿修复与验证（2026-11-18）

修复已在 Windows x64 / 60 Hz 本机验证。默认内核弹幕随屏幕刷新呈现，应用层弹幕也随
同一回调连续移动；两种模式各连续采样 60 秒，均通过更新频率、暂停、跳转、倍速和
窗口生命周期检查。源码基线为 `13752862`，本次修改保留在工作区。

本文保留第一阶段的修改与结果。随后用户反馈观感仍有波动，第二阶段增加了原生
弹幕视觉时钟、固定显示时间采样和应用层平移变换，并把时钟校正幅度从 10% 收紧
到 2%；详情及后续验证见 [弹幕运动验证](danmaku-motion-2026-11-18.md)。
原生视觉时钟实验随后按用户的维护偏好撤回，最终默认采用应用层方案，保留本次
应用层优化；当前版本沿用项目原来的内核 DLL。

## 原因与修改

旧播放器使用设为 16 毫秒的 `DispatcherTimer`。上个会话实测更新间隔中位数约
31.5 毫秒，P95 约 46–50 毫秒。应用层另外使用 33 毫秒定时器，并直接读取约每
100 毫秒更新一次的原生播放进度，因此横坐标约 100 毫秒才跳一步。

- `PlayerView` 改用 `CompositionTarget.Rendering` 调用原生 Tick 和应用层弹幕绘制，
  同一呈现时间只处理一次。进度条和章节菜单保留 200 毫秒更新周期。
- 移除应用层独立的弹幕定时器。`PlaybackRenderClock` 使用单调时钟在原生进度事件
  之间推进坐标，并应用实际设置的倍速。小误差以最多 10% 的速度校正；暂停、缓冲、
  停止和失败冻结，显式跳转与换源立即对齐，大于 0.5 秒的原生时间突变也立即对齐。
  超过 0.5 秒没有原生进度时停止继续外推。进度保存仍使用原生上报值。
- 最小化时解除屏幕刷新订阅，通过 33 毫秒后台定时器继续处理解码、音频及播放事件。
  恢复后停止后台定时器并重新订阅屏幕刷新；关闭播放器解除订阅并停止后台定时器。

弹幕横坐标，并比较相邻帧中同一条弹幕的移动。两个模式均在所有相邻采样帧中前进。
原始采样保存到 `kernel-samples.json` 和 `overlay-samples.json`。

弹幕刷新专项共 28 条断言通过，覆盖两种模式的 60 秒更新、暂停后固定坐标、暂停时
0.25 秒跳转立即对齐、稳定后的 2 倍速连续推进、各两轮最小化/恢复，以及关闭清理。
倍速测试允许时钟设计中的 10% 校正速度，并检查逐帧时间持续前进。两种模式的
倍速原始采样另存为 `kernel-rate-samples.json` 和 `overlay-rate-samples.json`。

HTTP 播放、字幕、弹幕、截图、续播、设置、服务器和销毁检查。现有真实 WinUI
原生播放器回归通过 29 条断言，验证本地 XML、字号/透明度/过滤、跳转重建、
换源选择渲染器和系统媒体会话；进程退出码为 0。

标准 x64 Debug、Release 及集成项目编译均为 0 警告、0 错误。
Release 的 `--verify-runtime` 启动检查通过，退出码为 0。

## 本机证据与复现

证据位于 `apps/windows/artifacts/danmaku-smoothness-20261118/`：

- `summary.json`：源码基线、输入/程序集/内核 DLL 哈希及验证汇总。
- `full-60s/`：逐帧采样、统计、28 条断言和进程退出状态。
- `integration/results.json`、`integration.log`：410 条集成断言及日志。
- `native-ui/results.json`、`native-ui/process-result.json`：29 条真实 WinUI 断言和退出状态。
- `release-runtime.json`、`release-process-result.json`：Release 启动检查。

在 `apps/windows` 目录运行 Debug exe，设置独立的绝对路径 `OCP_DATA_DIRECTORY`，
传入 `--verify-danmaku-cadence=<新结果目录> --open=<至少70秒的视频路径>` 即可复现。
采样时保持 60 Hz 或更高刷新率的窗口可见，专项本身会执行最小化/恢复检查。

本轮实测覆盖 Windows x64 / 60 Hz 与本地合成视频。120 Hz、ARM64 和外部网络
缓冲场景尚未实测；缓冲冻结和进度中断通过确定性时钟回归验证。
