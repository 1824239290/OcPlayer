# 共享弹幕加载编排

开启 OcPlayerCore 后，DanmakuLoadOrchestrator 的自动和手动入口通过 Core 中的
可继续执行流程运行。Core 决定四层匹配、逐请求预算、候选选择、缓存分支、
正文转换、播放器就绪/注入顺序和片头来源优先级。macOS 驱动器执行 Core 请求的
文件、网络、缓存与播放器动作，并回传结果和当前播放代次；网关网络动作继续
使用既有重试/解析封装和 Core 连接池。自定义 URLProtocol 仍可用于注入测试。

指纹完成后才开始默认三十秒匹配预算，每次请求之前都检查；在途请求不会被
预算截断。缓存快路径不计算指纹、不访问匹配网关。网关级故障短路后续层，
参数/业务/解码/4xx 错误仍可换参数降级。预算中断返回可重试失败，完整空结果
瀑布才返回未匹配。手动选择沿用强制片头重解析和映射代次保护。

共享正文转换保留原版前三个 ASCII 逗号字段、Swift 数字/Unicode 空白判定、
overlay 稳定排序以及不带 ID 的 Erika JSON。片头来源在弹幕上屏后查询，依次
采用缓存、并行社区源、学习值、兄弟集和正文检测；别名与 AniList 解析先于
社区源批量查询。输出 JSON 保留 Int64 标识符。

新增保护覆盖两个 await 后竞态：播放器就绪期间代次切换不会对同一 UUID 继续
注入；已上屏后取消别名查询不会继续解析 ID 或写入片头缓存。原有原版流程
保留在 runAutomaticNative/runManualNative，转换函数也保留为独立对照。

RustDanmakuFlowTests 对照 1200 组数字/Unicode 输入和三种输出路线、手动与缓存
自动入口，以及以上两种竞态。原有 29 个加载编排测试也通过共享入口运行。
Core 合约与原始验证记录在 OcPlayer-Core/docs/danmaku-flow-contract.md 和
对应 validation 目录。App 侧学习晋升推广、旧独立加载器替换和整体验收仍在推进。
