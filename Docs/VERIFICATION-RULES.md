# 验证与计数纪律

面向上游改代码、跑测试、**上报数字**的人。这份文件存在的原因很直接：**规矩写在 `CLAUDE.md` 里等于没写**（它被 `.gitignore:38` 忽略、从未入过库，clone 仓库的人读不到）。所以要长期生效的规矩必须放在这里。

每条规矩都附一个**当天真实翻车**的反例。规矩会被忘记，反例不会。

---

## 一、判据自身必须先被证伪，再拿去判结论

**做法**：构造一个"已知该失败"的输入，看判据是否给红。给绿 ⇒ 判据无效，先修判据。

```
反例  2026-11-03 复现次数统计：次数从 3 改到 8，每一版在当时都对
      → 因为它数的是"跑了多少轮"，不是"归因有多可靠"
      → 换成「栈是否逐符号一致」后，8/8，不再需要维护计数
```

## 二、结论要写明「如果我错了，会在哪里露出来」，然后真去查那个地方

这是本项目最有效的一条。被拦下来的错误，全部是因为有人去查了"露出来的地方"。

```
反例  判「某个包没跑过测试」→ 依据是 Packages/<pkg>/.build 不存在
      实际产物在 --scratch-path /tmp/data-pkg-<pkg>（为不污染验收产物）
      露出来的地方：find /tmp -name 'data-pkg-*'，而不是只看 Packages/
```

## 三、任何计数必须贴完整原始输出，不许只贴过滤后的

**你贴了什么，别人就只能核什么。** 过滤条件一旦丢了信息，被丢的那部分就再也无法被发现。

```
反例  grep 'Executed .* tests'   → 筛掉 swift-testing 行，四包漏报 34 条（720 应为 754）
反例  grep -c 'open()'           → 栈里符号是 __open，带括号写法根本不存在，误判"没阻塞"
反例  strings | grep 中文        → 多字节被过滤，误判"探针没编进去"
反例  ls /tmp/sample-59959.txt   → 真名 ocp-sample-59959.txt，误判"没落盘"
```

**共同结构**：先设定"我预期它长什么样"的查找条件，再把"没找到"当作"不存在"。
**正确方向相反**：按内容找，不按形状找——判分类用 `classify()` 不用具体 IP；判宿主用 `Process: … [PID]` 不用文件名；判源码用 `git show <path>` 不用行号。

## 四、上报测试数：四格 + 三个标注

```
四格   唯一用例数 / executed / passed / skipped / failed
       注意 executed 含 skipped，passed 不含，两者不是一回事
```
```
标注① 来源：逐条 Test case 计数 还是 Executed N tests 汇总行（块缓冲会吃行，二者会差）
标注② 分母：平台（macOS / iOS / SwiftPM）+ 是否含 swift-testing + git grep 还是 grep -r
标注③ 跨轮只能同口径相减：executed 只能减 executed
```

```
反例  43 / 79 / 81 / 80   只搜一个地址 vs 把 192.168.1.10 这类样例算进真实地址
                          三个分母指向同一个结论，但报数不写口径就是半个假话
反例  720 / 754           四包漏了 MetadataKit 的 swift-testing 34 条
反例  24 = 829 − 805      「含 skip 的 executed」减「不含 skip 的 passed」= 无意义的数
                          正确：829 = 805 + 19 + 5，那个 5 是「仅 iOS 19 − 仅 macOS 14」的净差，没有独立身份
反例  19 = 16 + 3         把 XCTSkip 调用点数当成跳过用例数
                          实际 18 条类级 setUpWithError 整类跳过 + 1 条单条跳过
反例  805 vs 824          忘了标「唯一用例数」，平台差异无处可查
```

## 五、跳过 ≠ 未验证

同一批用例在一个平台跳过、在另一个平台真跑并通过时，**不能记成「未验证」**。

```
实测  macOS 19 条 skip 里 18 条在 iOS 那轮真的执行且全 passed
      CI 里真正一次没跑过的只有 4 条，不是 19+3=22
```

同时要区分两件事：**按平台条件合法跳过**（如 `#if !os(iOS) throw XCTSkip`）与**用 skip 掩盖失败的断言**。后者才是假通过——`AppTests/SettingsLayoutTests.swift:35-36` 的注释写的就是这个区别，那个类却用了类级 skip；二者不矛盾，但必须写清楚。

## 六、工具的适用域（用错工具产出的是假证据）

| 工具 | 能判 | 不能判 |
| --- | --- | --- |
| `strings` | 英文符号在不在二进制里 | 中文（多字节被过滤）；96.9MB 之后的区域（只扫约 58%） |
| 主可执行文件 | — | Debug 符号（在 `OcPlayer.debug.dylib` 里，不在主 stub） |
| `log` 行数 | 有输出时执行到了哪 | 没输出时"没发生"（块缓冲；甚至整条记录可能从未写出） |
| `mtime` | 内容**可能**变了 | 内容**是否**变了（同内容可换时刻） |
| `lsof` | 有没有列出锁文件 | 有没有持有锁 |
| 日志时间跨度 | — | 进程存活时长（空闲无事件可写；用 `ps`/`pgrep`） |
| `ps -o %cpu` | — | 瞬时 CPU（是衰减均值；启动后几秒会虚高） |

**字节级判据**（唯一不受时间戳/编码影响的）：
```bash
python3 -c "import sys;d=open(sys.argv[1],'rb').read();print(d.count(sys.argv[2].encode()))" <binary> <str>
```

## 七、证据归档：临时目录里的证据等于没有

`.o` 计数、`xcresult`、`sample` 栈一旦落在 `/tmp` / `/var/folders`，系统清理后**证据链只剩文字描述，复核能力归零**。

```
反例  --scratch-path /tmp/data-pkg-*  跑完四包 754 条全绿，
      但 .o 计数（1107/86/1281/24）在 /tmp，报告不写下就再也拿不出来
⇒ 结论要用到某个临时产物，就立刻把它的可复核形态写进 Reports/
```

## 八、对外动作必须留主语

`push` / 发版 / 改 protocol 这类离开本机的动作，执行前要有一句可追溯的认领，**与 `git commit` 分开授权**。

**2026-11-03 的教训**：13:26:05 有一次 `git push`（`git reflog show origin/main` → `update by push`），终态完全正确，但**认领缺了关键字段**。调度的 Chief 在 13:28 报「已推送」，**却没说自己就是执行者**，反而在群里问 Build「是不是你推的」；Player 和 Design 又各自去 reflog 里查是谁推的——**为一个两分钟前自己完成的动作，追了半小时。**

**这里的失败不是「忘了说」，是「说了但不完整」**：只有「推送发生过」这个结论，没有「谁推的、什么时候推的」这两个可核对的事实。

错因不是记性，是**拿「我以为的现场」下结论，而现场在两分钟前已经被自己改变了**。

**判据：认领里的每个字段都必须是「抄下来的」，不是「记出来的」。**

推完立刻跑下面这条，把整行原样贴进群——它一次给出 sha、时间、`update by push` 三个事实，不需要凭记忆写任何一项：

```bash
git reflog show origin/main | head -1
# 6ed9d70 refs/remotes/origin/main@{0}: update by push
```

**为什么复制而不记忆**：2026-11-03 那次，Chief 认领时凭记忆报了 13:28，实际推送是 13:26:05。**错的不是「没认领」，是时间戳的来源**。reflog 一直在，事后可逐字对账；而「某人说他在某时刻推了」永远对不上账。

**为什么 reflog 不记录执行者（这是架构决定的，不是工具缺陷）**：所有 Bot 共享同一个工作目录与同一套文件系统，从 git 看来这次 push 就是「这个工作副本」发出的——**物理上不存在能区分「哪个 Bot 或用户」的痕迹**。所以认领只能靠外部记录，不能指望翻 reflog 补出执行者。**知道这条，就不会再有人去 reflog 里找一个注定不存在的东西。**

## 九、调用成本必须被当成本被约束

**2026-11-03 的教训**：一次修背景图闪动的任务，五个 Bot 并行约两小时，消耗 **21 亿 token**，其中 04–05 两小时占 **12.1 亿**。用户明说：**"我要的是有效率的团队，不是一点破事说半天没结果的团队"**。

> **本节数字的口径**（2026-11-03 19:1x 复核，来源：`~/.dsh/sessions/` 当天 20 个会话的逐次 `usage` 记录）：
> 全天 **2,135,407,693** token / **7,064** 次调用；输出仅占 **0.18%**，缓存读占 98.97%。
> 按每次调用记录时间分桶：04 时 6.63 亿 + 05 时 5.46 亿 = **12.09 亿**。
> 原文的「04–05 占 14.4 亿」「上下文 256 → 664,704」**未能复现**（实测单次输入峰值 688,488、最小 134），已按实测改正。
> **这是本文件第三条的一次自我执行：写进规矩的数字，同样要能被别人复算出来。**

### 成本是怎么起来的

不是"说得多"，是**每轮请求都重发全部历史**：

```
单会话最多 1,066 次调用 / 3.01 亿 token（次高 844 次 / 2.95 亿，均值约 34.9 万/次）
单次上下文峰值 688,488，最小 134
五个会话并行 ⇒ 全天 21.35 亿
```

输出 token 只占 **0.18%**。**成本 = 会话数 × 轮数 × 上下文长度**，三者相乘。

### 已实施的限制

**压缩**（`~/.dsh/profiles/desktop/cordis.patch.yml`）：

```yaml
- id: compaction-basic
  config:
    auto: true
    thresholdRatio: 0.35    # 默认 0.8，W=1M 时阈值 80 万，几乎不触发
    retainRatio: 0.12
    compactionRetries: 2
```

实测效果：重启后单次调用上下文从 **34 万级降到 1–4 千级**。

**调度**（dsh 无 provider 级限流插件，只能靠纪律）：

1. **默认单个 Bot 作业**，除非任务能切成互不相干的两块
2. **不做多方独立核验**——一个 Bot 做，调度者抽查关键点。今晚"五个人各自查谁推的"是反例
3. **奔着结果去**——修完、测完、报一句结论即止。不写复盘、不做自我批判、不互相评价
4. **阶段完成即断会话**，不在同一会话里往返数十轮

### 判据

**每次发言前问：这句能给用户带来新信息吗？不能就不发。**

只在这四种情况开口：发现真错误、改变计划、阻塞项需用户决策、用户直接问。
