# 发版前修复计划

基线：2026-11-06 审查的 4 个 P1、2 个 P2。范围是修复与回归验证，不包含发布。原始证据见同目录 REVIEW.md 与 verification-logs.zip。

## 实施顺序

拆成四个可独立审查的提交：① MoviePilot 会话与凭据归属（P1 #1/#4）；② 媒体仓储与最终进度归属（P1 #2/#3）；③ 多源字幕（P2 #5）；④ 精确续播（P2 #6）。前两项优先完成。各提交先跑定向回归，全部完成后再跑发布门禁。

## ① MoviePilot：请求、登录、回滚绑定同一会话

代码范围：MoviePilotAPIClient、MoviePilotStore 的配置入口、MoviePilotSearch 的 SSE 请求，以及 App 层 MoviePilotCoordinator。

- 统一配置改绑与会话失效入口：服务器或账号改变、手动登录、登出时，先作废旧会话，再安装新配置。避免协调器直接改变 store，而客户端还认为旧请求有效。
- 请求进入时捕获不可变的 baseURL、会话身份、token；URL 构造不再在重试期间读取可变的 store.baseURL。
- 首发、退避结束、401 重放、响应返回与状态提交前都校验身份；过期请求按取消处理，不写用户错误位，也不触发新会话的静默重登。
- 区分会话更换与同会话的 token 更新。合法的 401 静默重登可以更新 token 后重放；不能因为刷新自身推进凭证代次而误取消正常请求，也不能让旧会话借新凭据重放。
- 手动登录对 token 请求、用户信息请求、成功提交和失败清理做同一尝试身份校验。协调器的 profile、boundServerID、authError、isLoggingIn 与凭据回滚只由当前尝试更新。
- 401 通知清理只有客户端确认代次仍有效时才更新 UI；补查用户信息刷新与 SSE 的迟到响应是否遵守相同规则。

验收：A 的 503/超时请求在切 B 后不再重试；B 不收到 A 的 token、用户名或密码。登录挂起后登出不会恢复 token。旧登录成功、旧登录失败及旧通知均不能覆盖较新的登录。正常 401 单飞重登仍成功，POST 的瞬态错误不重放策略保持有效。

## ② 媒体数据面：仓储创建与最终写回同时修

代码范围：MetadataCoordinator、AppModel+Playback、MediaRepository 的会话退出与进度写回，以及需要接收显式租户快照的 MetadataStore API。

- currentRepository 等待前记录服务器实例与会话代次；等待后检查取消、实例与代次，再复查 repository。只有当前会话能安装仓储，同会话的并发调用复用同一实例。
- 播放开始时绑定元数据会话身份；finishReporting 在切服前同步捕获原租户、条目、位置、时长和快照时刻。异步写回不得重新选择“当前服务器”。
- 最终进度使用显式租户的专用落盘入口。原仓储仍有效时更新其内存投影；原会话已退出时仍可把已捕获的最终快照写入原租户磁盘，不能为此重新启用旧仓储的普通响应写入。
- 保留 shutdown 对旧网络响应的写盘拦截；最终快照与较新进度按时刻或序号判定先后，避免快速 A→B→A 后迟到的最终写回覆盖更新的状态。
- 检查详情已看状态回写的第二次异步更新，避免旧详情响应通过协调器再次写到新仓储。

验收：建库期间 A→B、A→登出均不会安装 A 的旧仓储；同会话并发获取只创建一个仓储。A、B 使用相同 itemID 时，A 的最后 60 秒进度只落 A，B 完全不变。退出期间合法最终进度保留，旧网络响应仍被拦截；快速切回 A 不会把较新的进度倒退。

## ③ 字幕：由当前播放源决定列举与缓存

代码范围：MediaServer 协议、Jellyfin/Emby 字幕实现、ExternalSubtitle 身份与下载缓存、AppModel+Playback，以及所有协议桩。

- 为字幕列举传入当前 request.sessionContext.mediaSourceID，Jellyfin/Emby 均严格匹配该源。仅在没有源 ID 的旧服务端兼容路径采用明确的首选源规则；指定源不存在时不要静默取第一份。
- 字幕身份与缓存文件名包含租户、媒体源、轨道索引和格式，使用稳定且安全的路径编码，防止不同服务器或不同版本互相覆盖。
- 自动换源后撤销旧字幕批次并为新源重新列举；沿用既有播放代次守卫，核对旧批次 defer 不会解除新批次的加载状态。
- 原字幕缓存保留，交给已有维护策略处理，无需发版前清空用户缓存。

验收：首源不可播放而选第二源时，下载的是第二源字幕；自动换源后字幕随源切换。同 itemID/index 的不同租户、不同源不会共用缓存路径。旧批次迟到不能挂载到新引擎，单源和无源 ID 的兼容场景正常。

## ④ 续播：执行请求里的精确位置

代码范围：PlaybackController.openPreparedRequest、PlaybackRequest 的构造入口与后台恢复/手动重试入口。

- 打开流程执行所有合法且有限的显式正续播位置，撤掉其内部的 30 秒门槛；继续使用已有就绪等待、播放代次校验和片尾定位边界。
- 是否采用 30 秒启发式由手动重试等产品入口决定。后台故障恢复直接采用精确位置，0 秒表示从头开始。

验收：1、20、29、30、40 秒均正确定位；0 秒从头播放；无效数值不送入内核。打开失败、换片或重开时，旧定位任务不能影响新引擎。真机在前 30 秒内后台故障恢复后不从头播放。

## 回归与发布门禁

1. 把现有 5 个复现转成断言正确行为的回归测试，先在未修代码上确认失败。原始 .swift.txt 与日志继续完整保留。
2. 网络退避、建库等待、登录响应和字幕下载使用可控闸门；消除依赖 sleep、抖动延迟或多轮碰窗口的复现方式，覆盖两种响应到达顺序。
3. 各提交运行受影响包与 App 定向测试；全部修复后运行双端 AppTests、11 个 SwiftPM 包，以及 macOS/iOS arm64 Release 构建。记录 passed/skipped/failed 与完整原始输出，校验产物版本及 dSYM UUID。
4. 使用真实 Jellyfin/Emby 多版本媒体验证字幕与换源；验证真实 MoviePilot 改绑与登录取消；真机验证后台恢复。
5. 单独复验已记录的高密度 CJK 字幕内核 abort。若仍存在，需要内核修复或经问题片源验证有效的缓解；不能以普通错误提示或未经验证的换渲染开关替代。

发版条件：4 个 P1 的反向回归全部通过；2 个 P2 修复通过；双端门禁通过；实际片源与真机验收完成；已知内核崩溃风险得到明确处理。届时更新 REVIEW.md 的修复状态与验证证据。
